# Шпаргалка по планировщикам задач в Linux: Cron и Systemd Timers

Краткое руководство по настройке фоновых задач и задач по расписанию: от быстрого `cron` до надежных юнитов `systemd`.
----------------------------------------------------------------------------------------------------------------------------
## 1. Cron (Классический планировщик)

Подходит для простых задач (очистка кэша, легкие скрипты) и работы внутри Docker-контейнеров.

### Основные команды управления
* `crontab -e` — открыть расписание текущего пользователя в редакторе.
* `sudo crontab -e` — открыть расписание пользователя `root` (для системных задач).
* `crontab -l` — вывести список всех текущих задач.
* `journalctl -u cron` — проверить, запускал ли `cron` задачу по расписанию.

### Архитектура строки `crontab`
Каждая задача — это одна строка, состоящая из **5 полей времени** (разделенных пробелами) и команды:

```text
* * * * * /полный/путь/к/скрипту.sh >> /var/log/script.log 2>&1
│ │ │ │ │
│ │ │ │ └── День недели (0-7, где 0 и 7 — Вс, 1 — Пн, 1-5 — будни)
│ │ │ └──── Месяц (1-12)
│ │ └────── День месяца (1-31)
│ └──────── Час (0-23)
└────────── Минута (0-59)
```

### Популярные шаблоны времени
* `0 4 * * *` — каждый день ровно в `04:00`.
* `*/15 * * * *` — каждые 15 минут.
* `0 */6 * * *` — каждые 6 часов (4 раза в сутки: в 00:00, 06:00, 12:00, 18:00).
* `30 9 * * 1-5` — по будням (Пн–Пт) в `09:30`.
* `@reboot` — один раз сразу после перезагрузки сервера.

### 3 главных правила, чтобы `cron` не сломался
1. **Полные пути:** У `cron` урезанный `PATH` (`/bin:/usr/bin`). Всегда указывайте путь от корня (`/opt/ops/backup.sh`).
2. **Логирование вывода:** `cron` не показывает вывод в терминал. Всегда перенаправляйте вывод и ошибки в файл: `>> /var/log/task.log 2>&1`.
3. **Экранирование `%`:** Символ процента в `crontab` ломает строку (воспринимается как перенос строки). Пишите с обратным слэшем: `date +\%F`.

## 2. Systemd (Сервисы и Таймеры)

Современный стандарт Linux. Используется для важных задач (бэкапы, мониторинг) и постоянно работающих приложений (бэкенды).

**Главное правило:** Одна задача — отдельные файлы в директории `/etc/systemd/system/`.

### Вариант А: Постоянный сервис (работает 24/7, например бэкенд)
Создаем один файл: `/etc/systemd/system/my-backend.service`

```ini
[Unit]
Description=Мой основной бэкенд
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/app
ExecStart=/usr/bin/python3 /opt/app/main.py
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

**Порядок запуска постоянного сервиса:**
```bash
sudo systemctl daemon-reload                # 1. Перечитать конфиги после создания/правки файла
sudo systemctl enable --now my-backend      # 2. Добавить в автозагрузку и сразу запустить
sudo systemctl status my-backend            # 3. Проверить статус (active/running)
```

### Вариант Б: Задача по расписанию (Таймер + Сервис)
Создаем **пару файлов** с одинаковым именем в `/etc/systemd/system/`.

**1. Файл сервиса (`/etc/systemd/system/backup.service`)** — описывает, *что* делать:
```ini
[Unit]
Description=Ночной бэкап базы данных

[Service]
Type=oneshot
ExecStart=/opt/ops/backup.sh
```
*(Примечание: секция `[Install]` и `Restart=` здесь не нужны, так как запуск контролирует таймер).*

**2. Файл таймера (`/etc/systemd/system/backup.timer`)** — описывает, *когда* запускать:
```ini
[Unit]
Description=Расписание для ночного бэкапа

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
* `Persistent=true` — если сервер был выключен в момент запуска, задача выполнится сразу после включения.
* Примеры `OnCalendar`: `*:0/5` (каждые 5 минут), `Mon 09:00` (по понедельникам в 09:00). Проверить формат можно командой `systemd-analyze calendar "*:0/5"`.

**Порядок запуска таймера (включаем именно `.timer`, а не `.service`!):**
```bash
sudo systemctl daemon-reload                # 1. Обновить конфигурацию systemd
sudo systemctl enable --now backup.timer    # 2. Включить и запустить таймер
systemctl list-timers                       # 3. Посмотреть список таймеров и время до запуска
```

## 3. Шпаргалка по управлению и логам `systemd`

| Действие | Команда |
| :--- | :--- |
| **Запустить / Остановить / Перезапустить** | `sudo systemctl start\|stop\|restart <имя>` |
| **Применить изменения в `.service` файле** | `sudo systemctl daemon-reload` |
| **Посмотреть все логи сервиса** | `journalctl -u <имя>.service` |
| **Смотреть логи в реальном времени** | `journalctl -u <имя>.service -f` |
| **Показать только ошибки** | `journalctl -u <имя>.service -p err` |
| **Последние 50 строк лога** | `journalctl -u <имя>.service -n 50` |

## 4. Боевая обвязка для важных задач (`flock` + `timeout` + мониторинг)

Чтобы фоновая задача не сломала сервер и не «умерла втихую», запуск оборачивают в три уровня защиты:

1. **`flock -n /run/lock/task.lock`** — защита от дублей. Если прошлая копия скрипта еще не закончила работу, новая сразу выйдет, не создавая очередь.
2. **`timeout 30m`** — защита от вечного зависания. Если скрипт висит дольше 30 минут, система прибьет его сигналом `SIGTERM` и вернет код `124`.
3. **`&& curl -fsS <URL>`** — «пульс» (Dead Man's Switch). Если скрипт завершился без ошибок (`0`), он дергает ссылку сервиса мониторинга (например, *Healthchecks.io* или *Uptime Kuma*). Если пинга не было — дежурному летит тревога.

### Как это выглядит в `cron`:
```cron
0 3 * * * /usr/bin/flock -n /run/lock/backup.lock /usr/bin/timeout 30m /opt/ops/backup.sh && /usr/bin/curl -fsS https://example.com >> /var/log/backup.log 2>&1
```

### Как это выглядит в `systemd` (`/etc/systemd/system/backup.service`):
```ini
[Unit]
Description=Надежный ночной бэкап

[Service]
Type=oneshot
# В systemd вместо внешнего timeout можно использовать встроенный параметр:
TimeoutStartSec=30m
ExecStart=/usr/bin/flock -n /run/lock/backup.lock /opt/ops/backup.sh
# Выполнится только при успешном завершении ExecStart:
ExecStartPost=/usr/bin/curl -fsS https://example.com
